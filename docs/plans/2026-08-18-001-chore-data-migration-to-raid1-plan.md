# chore: перенос данных с /mnt/data-tmp на зеркало /mnt/data и переключение DATA_PATH

## Product Contract

### Summary

Перенести живые данные сервисов с временного каталога `/mnt/data-tmp` (лежит на системном NVMe внутри 100-гигабайтного LVM-тома) на RAID1-зеркало, смонтированное в `/mnt/data`, переключить `DATA_PATH` в серверном `.env` и вернуть сервисы на штатный путь — не потеряв ни файла, ни прав доступа, и сохранив рабочий откат до момента, когда перенос подтверждён.

---

### Problem Frame

**Как получилось.** Прежний одиночный HDD, обслуживавший `/mnt/data`, вышел из строя. Как временное решение `DATA_PATH` в `.env` был переставлен на `/mnt/data-tmp` — каталог на системном диске. С тех пор все контейнеры, монтирующие `${DATA_PATH}`, физически пишут туда: на системный NVMe, внутрь корневого LVM-тома размером 100 ГБ, без какой-либо избыточности.

**Что изменилось.** Собрано зеркало RAID1: `/dev/md0` из двух дисков Seagate ST6000VN006 6 ТБ на целых дисках, ext4, монтируется по UUID через `/etc/fstab`, первичная синхронизация завершена (`[2/2] [UU]`), 5.4 ТиБ свободно. Оба диска прошли полный поверхностный SMART-тест без ошибок. Зеркало пустое.

**Кто пишет данные.** Пять развёрнутых сервисов монтируют `${DATA_PATH}`:

| Сервис | Что монтирует | Режим |
| --- | --- | --- |
| `samba` | весь корень `${DATA_PATH}` → `/data` | запись |
| `syncthing` | `users/andrew/sync` → `/data`, `public` → `/public` | запись |
| `filebrowser` | `public` → `/srv/public`, `users` → `/srv/users` | запись |
| `backrest` | `users` → `/backup/users` | только чтение |
| `opds-generator` | `public/library`, `public/ttrpg/rpg-guides` | только чтение |

`ytpod` данные не монтирует (только Redis в appdata). Сервисы `transmission`, `transmission-omg`, `stash`, `opml-generator` лежат с суффиксом `.disabled` — скрипты их не видят и не остановят, но их контейнеры могли остаться запущенными с прошлых времён.

**Почему это не «просто скопировать».** Четыре свойства этой конкретной установки делают наивный перенос опасным:

1. **Хост резолвит DNS только через AdGuard в Docker.** `./scripts/docker/stop.sh` без аргументов останавливает *все* сервисы, включая AdGuard, — и хост теряет разрешение имён. Останавливать можно только поимённо.
2. **Syncthing синхронизируется с внешними устройствами.** Если он поднимется на пустом или недокопированном дереве, он увидит массовое удаление и **разошлёт удаление партнёрам**. Для папки `users/andrew/sync` устройства-партнёры — единственная вторая копия: restic-планы в `backrest` бэкапят только `/backup/appdata`, каталог `users` не бэкапится никуда.
3. **Файлы Syncthing принадлежат `root:root`.** Эта сборка образа игнорирует `PUID`/`PGID` (описано в `ENVIRONMENT.md`), поэтому в дереве данных смешаны владельцы `root:root` и `1000:1000`. Копия обязана сохранить эту смесь как есть.
4. **Samba хранит метаданные macOS в расширенных атрибутах файлов** (`vfs objects = ... streams_xattr`, `fruit:metadata = stream`). Обычный `cp -r` их потеряет молча — ни `ls`, ни интерфейс сервиса этого не покажут. При этом в том же конфиге стоят `ea support = no` и `store dos attributes = no`, поэтому реальный объём атрибутов в дереве надо измерить, а не предполагать.

**Что создаёт сам переезд.** В `/etc/fstab` у массива стоит `nofail` — осознанно, чтобы мёртвый массив не ронял загрузку headless-сервера в аварийную консоль. Побочный эффект появляется только после переезда: если массив не соберётся, `/mnt/data` окажется пустым каталогом на корневой файловой системе, и **Docker при старте контейнера сам создаст недостающие каталоги bind-маунтов** — от `root:root`, на корневом диске. Сервисы начнут работать на пустышке поверх корня. До переезда этой опасности не было, потому что данные и так лежали на корне.

Важная деталь механики: каталоги создаёт именно Docker, а не скрипты репозитория. `ensure_service_dirs()` в `scripts/docker/_lib.sh` обрезает строку тома по первому двоеточию, а все тома данных записаны как `${DATA_PATH:-/mnt/data}/public:/srv/public` — функция получает обрубок `${DATA_PATH` и по нему ничего не создаёт. Единственный путь, который она реально обрабатывает, — `${HOME}/.config/rclone` у `backrest`. Из этого следует и форма защиты (U7), и то, что защита в самой `ensure_service_dirs()` была бы мёртвым кодом.

### Requirements

- **R1.** Все файлы из `/mnt/data-tmp` оказываются в `/mnt/data` с сохранением содержимого, владельцев, прав, жёстких ссылок, ACL и расширенных атрибутов.
- **R2.** Ни один процесс не пишет в исходное дерево во время копирования.
- **R3.** Полнота и точность копии доказана проверкой, которая ловит расхождение по правам и атрибутам, а не только по объёму.
- **R4.** После переключения `DATA_PATH` каждый из пяти сервисов монтирует каталоги с массива, что подтверждено на уровне Docker, а не на глаз.
- **R5.** Syncthing возвращается в работу без рассылки удалений партнёрам.
- **R6.** Сервисы читают и **пишут** через свои штатные интерфейсы на новом месте.
- **R7.** До явного гейта существует рабочий откат: вернуть `DATA_PATH` и передеплоить.
- **R8.** Если массив не примонтирован, каталоги данных не должны появляться на корневой файловой системе — ни при запуске деплоя, ни при автозапуске контейнеров после перезагрузки.
- **R9.** `/mnt/data-tmp` выводится из обращения только после того, как доказано, что на него ничего не ссылается; необратимое удаление — только после появления копии данных вне зеркала.
- **R10.** Документация репозитория перестаёт описывать временное состояние и описывает фактическое.

---

### Success Criteria

- Повторный `rsync --dry-run --itemize-changes` в ту же сторону не печатает ни одной строки изменений.
- `docker inspect` по каждому из пяти сервисов показывает источники монтирования на `/mnt/data`.
- Файл, записанный через сетевую шару Samba, физически оказывается на `/dev/md0` с ожидаемым владельцем.
- В Syncthing обе папки в состоянии `Up to Date`, партнёры не получили удалений.
- При отмонтированном массиве попытка деплоя и автозапуск контейнеров не создают каталогов на корне.
- `/mnt/data-tmp` переименован и выведен из обращения; после удаления освободившееся место видно в `df /`.

---

### Scope Boundaries

**В работе:** перенос данных, переключение `DATA_PATH`, возврат пяти сервисов на массив, защита от незамонтированного массива, вывод временного каталога из обращения, обновление документации.

#### Отложено на отдельную задачу

- **Первая холодная копия на 8 ТБ диск `sdd`.** Не входит сюда по решению из обсуждения. Но именно она — гейт для **необратимого удаления** в U9: пока копии вне зеркала нет, `rm -rf` делать нельзя, потому что каталог `users` не бэкапится ни в один restic-репозиторий. Переименование каталога (обратимое) остаётся в этом плане, само удаление ждёт холодной копии.
- **Автоматизация недельного бэкапа на `sdd`.**
- **`smartd` мониторит только `/dev/sda`** (`scripts/bootstrap.sh`, конфиг `/etc/smartd.conf`). Второй диск зеркала без наблюдения — отказ `sdb` пройдёт незамеченным. Отдельная правка, не блокирует перенос, но её цена растёт: после переезда зеркало становится единственным домом для `users`.
- **Виджет Homepage следит только за `/`** (`services/homepage/config/widgets.yaml`). После переезда заполненность массива не видна нигде.

#### Вне периметра

- Изменение состава сервисов, схемы каталогов и правил доступа Samba.
- Уменьшение или перераспределение корневого LVM-тома. Удаление `/mnt/data-tmp` возвращает место **внутри** корневой файловой системы; отдавать экстенты обратно в volume group — принципиально другая и куда более рискованная операция, здесь не делается.
- Перевод `backrest` на бэкап каталога `users` (сегодня его маунт `/backup/users` не используется ни одним планом).

## Planning Contract

### Key Technical Decisions

- **KTD1. Останавливаем писателей поимённо, а не `stop.sh` целиком.** *(session-settled: user-directed — выбрано вместо копирования «на живую» с догоняющим проходом: меньше риск расхождения.)* Останавливаются `syncthing`, `samba`, `filebrowser`, `backrest`, `opds-generator`, плюс любые осиротевшие контейнеры, найденные при инвентаризации. Полная остановка уронила бы AdGuard, а с ним разрешение имён на хосте. Traefik, Authelia, Cloudflared, Home Assistant и прочие продолжают работать — они данных не касаются. Управляет R2.

- **KTD2. Копируем `rsync` с полным набором сохранения метаданных, под `sudo`, в tmux.** Флаги: `-aHAXS --numeric-ids`. `-H` — жёсткие ссылки, `-A` — ACL, `-X` — расширенные атрибуты (метаданные Finder от Samba), `-S` — разрежённые файлы, `--numeric-ids` — не отображать имена пользователей. Под `sudo`, иначе владельцы не сохранятся. В tmux, потому что обрыв SSH или отключение хоста по UPS иначе убьёт процесс. Лог пишется самим `rsync` через `--log-file`, а не конвейером в `tee`: после конвейера `$?` показывает статус `tee`, и падение копирования выглядело бы успехом. Управляет R1.

- **KTD3. Доказательство копии — пустой повторный проход, а не сравнение объёма.** `du` на источнике и приёмнике **законно** различается из-за разрежённых файлов, жёстких ссылок, размера блока, каталога `lost+found` и однопроцентного резерва ext4. Сравнение объёмов даёт либо ложную тревогу, либо ложное спокойствие — оно не видит потерю расширенных атрибутов. Гейт: `rsync -aHAXSn --itemize-changes` печатает ноль строк. Управляет R3.

- **KTD4. Syncthing поднимается последним, отдельно от остальных.** Сначала папки ставятся на паузу в интерфейсе (до остановки), потом сервис поднимается уже после того, как копия доказана и остальные сервисы проверены. Причина в Problem Frame: поднятый на неполном дереве Syncthing рассылает удаления партнёрам, а документированное лечение (`Revert Local Changes`) уничтожает файлы, существующие только локально. То же правило действует и при откате. Управляет R5.

- **KTD5. Скрипты деплоя запускаются от обычного пользователя, никогда через `sudo`.** `services/backrest/docker-compose.yml` монтирует `${HOME}/.config/rclone`. Под `sudo` это превращается в `/root/.config/rclone`, `ensure_service_dirs()` создаст пустой каталог (это единственный том, который она реально обрабатывает), и backrest поднимется без доступа к rclone — все удалённые restic-репозитории молча отвалятся. Сами скрипты вызывают `sudo` там, где он нужен.

- **KTD6. Никогда не «чинить» права запуском `scripts/bootstrap.sh`.** Его `set_permissions` делает рекурсивный `chown -R 1000:1000` и `chmod -R 775/750` — рекурсивный chmod без режима `X` навешивает бит исполнения на **каждый файл**, а chown затирает `root:root`, который Syncthing проставил осознанно. На заполненном дереве это необратимо без заранее снятого манифеста и вызовет лавину метаданных для всех партнёров Syncthing. Права правятся точечно.

- **KTD7. Вывод временного каталога из обращения — через переименование с выдержкой.** `mv /mnt/data-tmp /mnt/data-tmp.DELETE-<дата>`, наблюдение, затем удаление — уже под гейтом холодной копии. Скрытая ссылка на старый путь при простом `rm -rf` привела бы к молчаливому пересозданию `/mnt/data-tmp` и записи на корневой диск; после переименования такая ссылка ломается громко. Управляет R9.

- **KTD8. Защита от незамонтированного массива ставится на двух уровнях.** Уровень скриптов: предполётная проверка в `do_deploy()` до создания каталогов и до `docker compose up` — если сервис использует `DATA_PATH`, а `DATA_PATH` описан в `/etc/fstab`, но не примонтирован, деплой прерывается. Проверка ставится именно в `do_deploy`, а не в `ensure_service_dirs()`: та не видит путей вида `${DATA_PATH:-/mnt/data}/...` вовсе (см. Problem Frame), и защита внутри неё была бы мёртвым кодом. Уровень файловой системы: подлежащий каталог `/mnt/data` под точкой монтирования делается неизменяемым (`chattr +i`), пока массив отмонтирован, — тогда Docker при автозапуске контейнеров после неудачной сборки массива падает громко, вместо того чтобы создать каталоги на корне. Второй уровень нужен потому, что после перезагрузки контейнеры поднимает демон Docker по `restart: unless-stopped`, минуя скрипты репозитория. Управляет R8.

### Assumptions

- Утилиты `getfacl` и `getfattr` (пакеты `acl`, `attr`) на сервере есть или могут быть установлены. Пустой снимок атрибутов трактуется как факт «атрибутов нет» **только** если утилиты присутствуют и завершились без ошибки.
- Объём данных в `/mnt/data-tmp` ограничен размером корневого LVM-тома (100 ГБ), поэтому полная сверка по контрольным суммам занимает порядка получаса, а не суток. Фактический объём измеряется в U1; если он окажется заметно больше ожидаемого, время сверки пересчитать до её запуска.

## Implementation Units

### U1. Предполётная проверка и инвентаризация

**Цель:** убедиться, что приёмник — действительно массив, что источник известен целиком, и закрыть путь появления каталогов на корне на уровне файловой системы.

**Требования:** R8.

**Зависимости:** нет.

**Файлы:** изменений в репозитории нет; артефакты складываются в `/opt/homelab/appdata/migration-2026-08-18/` (этот каталог попадает в удалённый restic через `backrest`).

**Подход:**

1. Доказать, что `/mnt/data` — примонтированный массив, а не каталог на корне.
2. Отрепетировать fstab, пока массив пуст: отмонтировать, посмотреть, что под точкой монтирования, **сделать подлежащий каталог неизменяемым**, вернуть `mount -a`. Это единственный момент, когда репетиция бесплатна, а `chattr +i` ставится только на пустой каталог под точкой монтирования и на смонтированный массив никак не влияет.
3. Составить инвентарь **по факту**: какие контейнеры — включая остановленные — имеют источники монтирования в `/mnt/data-tmp`. Так найдутся осиротевшие контейнеры отключённых сервисов, которых скрипты не видят.
4. Проверить объём, число файлов и иноды.
5. Найти симлинки внутри источника, указывающие на сам `/mnt/data-tmp` абсолютным путём, — после переезда они сломаются.
6. Убедиться, что инструменты для снятия манифеста установлены (сам манифест снимается в U2, после остановки писателей).

```bash
findmnt /mnt/data
findmnt -T /mnt/data-tmp
cat /proc/mdstat
stat -c '%d %n' /mnt/data /mnt/data-tmp /

sudo umount /mnt/data
ls -la /mnt/data
sudo chattr +i /mnt/data
sudo mount -a
findmnt /mnt/data

docker ps -aq | xargs -r docker inspect \
  --format '{{.Name}} {{.State.Status}}{{range .Mounts}} {{.Source}}{{end}}' | grep data-tmp

sudo du -sh /mnt/data-tmp
sudo find /mnt/data-tmp -xdev | wc -l
df -h /mnt/data /; df -i /mnt/data /

sudo find /mnt/data-tmp -type l -lname '*data-tmp*'

command -v getfacl getfattr || sudo apt install -y acl attr
sudo mkdir -p /opt/homelab/appdata/migration-2026-08-18
```

**Проверка:**

- `findmnt /mnt/data` показывает источником `/dev/md0`; номера устройств у `/mnt/data` и `/` различаются.
- Под точкой монтирования пусто или лежит только старая заглушка; после `chattr +i` и `mount -a` массив снова на месте и пишется нормально (`sudo touch /mnt/data/.probe && sudo rm /mnt/data/.probe`).
- Список контейнеров, пишущих в `/mnt/data-tmp`, зафиксирован. Всё, что не входит в пятёрку (`syncthing`, `samba`, `filebrowser`, `backrest`, `opds-generator`), выписано отдельно — эти контейнеры останавливаются в U2.
- Свободного места на `/mnt/data` кратно больше объёма источника; инодов хватает.
- `getfacl` и `getfattr` доступны.

### U2. Остановка писателей, доказательство тишины и снимок метаданных

**Цель:** остановить всё, что пишет в источник, не уронив разрешение имён на хосте, и снять слепок прав уже с неподвижного дерева.

**Требования:** R2, R3.

**Зависимости:** U1.

**Подход:**

1. **На клиентских машинах** отмонтировать сетевые шары Samba (на macOS — «извлечь» том в Finder). Иначе переподключающийся Finder начнёт писать в дерево посреди работы.
2. **В интерфейсе Syncthing на сервере** записать для каждой папки её тип, состояние `Ignore Permissions`, число файлов, каталогов и объём (поле Global State) — всё это сверяется в U8. Затем поставить папки на паузу («Pause All» в блоке Folders).
3. **Пауза на устройствах-партнёрах не нужна** — проверено на месте 2026-08-18: все пять папок имеют тип **Receive Only**, то есть сервер только принимает изменения и сам партнёрам ничего не отправляет. Сценарий «сервер увидел неполное дерево и разослал удаление» этой конфигурацией закрыт. Остаточный риск другой и мельче: на неполном дереве сервер начнёт скачивать недостающее заново, а кнопка `Revert Local Changes` уничтожит то, что есть только на сервере — жать её нельзя.

**Снято на 2026-08-18 (сверять в U8):** итого 4 053 файла, 262 каталога, ~8.6 GiB. BookLibrary `/public/library` — 621/8/2.09 GiB; Documents `/data/documents` — 674/75/298 MiB; Knowledge base `/data/knowledge-base` — 1900/61/121 MiB; TTRPG `/public/ttrpg` — 597/58/6.01 GiB; TTRPG Obsidian `/data/ttrpg` — 261/60/89.6 MiB. Все пять: Receive Only, `Ignore Permissions = Yes`.
4. Остановить пять сервисов **поимённо**. `stop.sh` делает `docker compose down`, то есть удаляет контейнеры; сеть `traefik-net` объявлена внешней и переживает это.
5. Остановить осиротевшие контейнеры, найденные в U1 (`docker stop <имя>`), и повторить инвентаризацию.
6. Доказать, что источник никем не занят. `fuser` — без ключа `-m`: с ним проверялась бы вся корневая файловая система, а `/mnt/data-tmp` — каталог на ней, и в ответ пришёл бы список из половины процессов системы.
7. Снять манифест прав, ACL и расширенных атрибутов. Ошибки не глушить: пустой файл атрибутов должен означать «атрибутов нет», а не «утилита не установлена».

```bash
cd /opt/homelab
./scripts/docker/stop.sh syncthing samba filebrowser backrest opds-generator

docker ps -aq | xargs -r docker inspect \
  --format '{{.Name}} {{.State.Status}}{{range .Mounts}} {{.Source}}{{end}}' | grep data-tmp

sudo fuser -v /mnt/data-tmp
sudo lsof +D /mnt/data-tmp

cd /opt/homelab/appdata/migration-2026-08-18
sudo sh -c "find /mnt/data-tmp -xdev -printf '%y %m %u %g %p\n' | sort > manifest-before.txt"
sudo sh -c "find /mnt/data-tmp -xdev -type f -printf '%s %p\n' | sort > sizes-before.txt"
sudo sh -c "getfacl -R /mnt/data-tmp > acl-before.txt 2> acl-before.err"
sudo sh -c "getfattr -R -d -m - /mnt/data-tmp > xattr-before.txt 2> xattr-before.err"
wc -l manifest-before.txt sizes-before.txt acl-before.txt xattr-before.txt
wc -c acl-before.err xattr-before.err
```

**Проверка:**

- В инвентаре запущенных контейнеров нет ни одного с источником в `/mnt/data-tmp`.
- `fuser` и `lsof +D` по источнику не показывают процессов. Любая непустая выдача — блокер, а не шум. `lsof +D` обходит всё дерево и может идти несколько минут — запускать в tmux.
- `dig @127.0.0.1 dns.1218217.xyz +short` по-прежнему отвечает — AdGuard не задет.
- Файлы манифеста непусты; файлы ошибок (`*.err`) пусты. Пустой `xattr-before.txt` при пустом `xattr-before.err` — это факт «расширенных атрибутов нет», зафиксированный до переноса.

### U3. Копирование данных

**Цель:** перенести дерево целиком, сохранив метаданные.

**Требования:** R1.

**Зависимости:** U2.

**Подход:** запускать **в tmux** — обрыв SSH или отключение хоста по UPS иначе убьёт процесс. Проверка монтирования встроена в блок: при повторном запуске после перезагрузки массив может не собраться (в fstab стоит `nofail`), и копирование залило бы 100 ГБ на корневой диск. Обратить внимание на завершающие слэши: `/mnt/data-tmp/` (с ним) означает «содержимое каталога», без него получился бы вложенный `/mnt/data/data-tmp`. `--delete` не используется ни при первом запуске, ни при повторных: источник — это путь отката, его нельзя трогать.

```bash
tmux new -s migrate

mountpoint -q /mnt/data && \
sudo rsync -aHAXS --numeric-ids --info=progress2 --stats \
  --log-file=/opt/homelab/appdata/migration-2026-08-18/rsync.log \
  /mnt/data-tmp/ /mnt/data/
echo "rsync exit=$?"
```

Отсоединиться от сессии — `Ctrl+b`, затем `d`; вернуться — `tmux attach -t migrate`.

При обрыве повторять **весь блок целиком**, вместе с проверкой монтирования: `rsync` докопирует недостающее.

**Проверка:**

- `rsync exit=0`. Если ничего не выполнилось и код `1` — массив не примонтирован, копирование не начиналось: разбираться с массивом. Коды `23` и `24` (частичная передача / файлы исчезли по ходу) означают, что что-то писало в источник или файлы были недоступны — разбираться, не идти дальше.
- В логе нет строк с `error`, `failed`, `IO error`.
- Не осталось временных файлов оборванной передачи: `sudo find /mnt/data -name '.*.??????' -type f` — пусто.

### U4. Доказательство идентичности копии

**Цель:** доказать, что копия полная и точная, проверкой, которая ловит расхождение по правам и атрибутам.

**Требования:** R3.

**Зависимости:** U3.

**Подход:** главный гейт — повторный прогон в режиме «ничего не делать, показать что бы изменилось». Он сравнивает не только наличие файлов, но и размер, время, владельца, права, ACL и расширенные атрибуты, но содержимое файлов не читает. Поэтому следом идёт полная сверка по контрольным суммам **всего дерева**: обе стороны читаются целиком, сравнивается сумма от содержимого. Это ловит порчу, при которой размер и время совпали (сбойная память, контроллер), — единственный класс потерь, невидимый для основного гейта. При объёме до 100 ГБ проход добавляет порядка получаса и делается один раз. Запускать в tmux. Манифесты сравниваются без размеров каталогов: размер каталога на ext4 зависит от истории вставок и законно различается между источником и свежесозданным приёмником.

```bash
sudo rsync -aHAXSn --itemize-changes /mnt/data-tmp/ /mnt/data/ | tee /tmp/itemize.txt
wc -l /tmp/itemize.txt

sudo rsync -aHAXSnc --itemize-changes /mnt/data-tmp/ /mnt/data/ | tee /tmp/checksum.txt
wc -l /tmp/checksum.txt

cd /opt/homelab/appdata/migration-2026-08-18
sudo sh -c "find /mnt/data -xdev -printf '%y %m %u %g %p\n' | sed 's#^\(.*\)/mnt/data#\1SRC#' | sort > manifest-after.txt"
sudo sh -c "find /mnt/data -xdev -type f -printf '%s %p\n' | sed 's#/mnt/data#SRC#' | sort > sizes-after.txt"
sed 's#/mnt/data-tmp#SRC#' manifest-before.txt | sort > manifest-before.norm.txt
sed 's#/mnt/data-tmp#SRC#' sizes-before.txt | sort > sizes-before.norm.txt
diff manifest-before.norm.txt manifest-after.txt | head -30
diff sizes-before.norm.txt sizes-after.txt | head -30

getfattr -R -d -m - /mnt/data/public | head -20
stat -c '%U:%G %a %n' /mnt/data-tmp /mnt/data
```

**Проверка:**

- `wc -l /tmp/itemize.txt` — **ноль строк**. Это и есть гейт; при ненулевом результате разбирать каждую строку, дальше не идти. Единственное допустимое исключение — строка про сам корневой каталог приёмника, если владелец или права корня ещё не выровнены (см. последний пункт).
- Сверка по контрольным суммам всего дерева даёт ноль строк.
- `diff` обоих манифестов пуст, кроме строки `lost+found` (она есть только на ext4-приёмнике).
- Выборочный `getfattr` на приёмнике показывает те же атрибуты, что зафиксированы в `xattr-before.txt` (или так же пусто, если атрибутов не было).
- Владелец и права **самого корневого каталога** совпадают; если различаются — выставить вручную по значению из `stat` источника.

### U5. Переключение DATA_PATH

**Цель:** перевести конфигурацию на массив, сохранив рабочий якорь отката.

**Требования:** R4, R7.

**Зависимости:** U4.

**Файлы:** `/opt/homelab/.env` и `/opt/homelab/.gitignore` на сервере.

**Подход:** резервная копия делается с `-n` — повторный проход по этому юниту не должен перезаписать её уже переключённым значением, иначе откатываться будет нечем. `.env.bak-*` заранее вносится в `.gitignore`: файл содержит все секреты сервера, а `.gitignore` игнорирует только точное имя `.env`.

```bash
cd /opt/homelab
grep -q '^\.env\.bak-' .gitignore || echo '.env.bak-*' >> .gitignore
cp -n .env .env.bak-2026-08-18
grep -n '^DATA_PATH=' .env.bak-2026-08-18

sed -i 's#^DATA_PATH=/mnt/data-tmp#DATA_PATH=/mnt/data#' .env
grep -n '^DATA_PATH=' .env
```

**Проверка:**

- В `.env` значение `DATA_PATH=/mnt/data`, ровно одна строка.
- В `.env.bak-2026-08-18` значение `DATA_PATH=/mnt/data-tmp` — именно оно делает откат рабочим.
- `git status --short` не показывает `.env.bak-2026-08-18` среди неотслеживаемых файлов.

### U6. Страховка от незамонтированного массива

**Цель:** сделать невозможным молчаливое создание каталогов данных на корневой файловой системе, если массив не собрался.

**Требования:** R8.

**Зависимости:** U5. Юнит идёт до подъёма сервисов: сервисы ещё остановлены, поэтому отмонтировать массив для проверки можно без второго цикла остановки, а сама защита начинает действовать уже на деплоях U7.

**Файлы:** `scripts/docker/_lib.sh` (функция `do_deploy`).

**Подход:** предполётная проверка в `do_deploy()` — до вызова `ensure_service_dirs` и до `docker compose up`. Условие срабатывания берётся из `/etc/fstab`, а не из текущего состояния монтирования: проверять «только если `DATA_PATH` сейчас точка монтирования» бессмысленно, потому что в аварийном случае он ею как раз не является. Логика: если compose-файл сервиса ссылается на `DATA_PATH` и для `DATA_PATH` есть запись в `/etc/fstab`, но путь не примонтирован — прервать деплой с внятным сообщением. При `DATA_PATH` на корневой ФС (прежняя конфигурация, записи в fstab нет) проверка не срабатывает и поведение не меняется.

Проверка должна прерывать именно деплой: разбор томов в `ensure_service_dirs` идёт в конвейере, то есть в подоболочке, откуда `exit` не завершает вызывающий скрипт — ещё одна причина ставить проверку в `do_deploy`, а не внутрь разбора томов.

**Что взять за образец:** стиль вывода ошибки и раннего выхода — из существующих проверок в `scripts/docker/_lib.sh` (например `check_env`).

**Сценарии проверки:**

- Массив примонтирован → деплой сервиса с томами данных проходит как раньше.
- Массив отмонтирован → деплой прерывается с сообщением про непримонтированный массив, каталоги не создаются.
- Сервис без томов данных (например `adguard`) при отмонтированном массиве разворачивается нормально — проверка его не касается.
- `DATA_PATH` указывает на путь на корневой ФС без записи в fstab → проверка не срабатывает.

```bash
cd /opt/homelab
sudo umount /mnt/data            # сервисы ещё остановлены после U2
./scripts/docker/deploy.sh filebrowser   # ожидается ошибка
ls -la /mnt/data                 # ожидается пусто
./scripts/docker/deploy.sh adguard 2>&1 | tail -3   # ожидается успех
sudo mount -a
findmnt /mnt/data
```

**Проверка:** после неудачного деплоя `ls -la /mnt/data` пуст — ни одного созданного каталога; `adguard` при этом разворачивается; после `mount -a` массив на месте. Защита `chattr +i` из U1 дублирует это на уровне файловой системы для случая, когда контейнеры поднимает сам Docker после перезагрузки, минуя скрипты.

### U7. Деплой сервисов, кроме Syncthing

**Цель:** вернуть четыре сервиса на массив и убедиться, что монтирование ведёт туда.

**Требования:** R4.

**Зависимости:** U6.

**Подход:** запускать **от обычного пользователя, без `sudo`** (KTD5). Разворачивать по одному: `deploy.sh` останавливается на первой ошибке, а поштучный запуск не оставит половину сервисов удалёнными. Syncthing здесь **не разворачивается** (KTD4).

Перед деплоем `opds-generator` убедиться, что его каталоги на новом месте непусты, иначе Docker создаст на их месте пустые от `root:root`, и сервис отдаст устаревший каталог из своего кэша.

```bash
cd /opt/homelab
ls /mnt/data/public/library | head
ls /mnt/data/public/ttrpg/rpg-guides | head

./scripts/docker/deploy.sh samba
./scripts/docker/deploy.sh filebrowser
./scripts/docker/deploy.sh backrest
./scripts/docker/deploy.sh opds-generator

for s in samba filebrowser backrest opds-generator; do
  echo "=== $s ==="
  docker inspect "$s" --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}
{{end}}'
done
```

**Проверка:**

- Все четыре контейнера в состоянии `Up` (`./scripts/docker/status.sh`).
- В выводе `docker inspect` нет ни одного источника с `/mnt/data-tmp`.
- У `backrest` виден маунт конфигурации rclone из домашнего каталога пользователя, а не из `/root` — иначе деплой ушёл под `sudo`, и его нужно переразвернуть от обычного пользователя.

### U8. Возврат Syncthing и функциональная проверка

**Цель:** вернуть Syncthing без рассылки удалений партнёрам и убедиться, что сервисы читают и пишут на массив.

**Требования:** R4, R5, R6.

**Зависимости:** U7.

**Подход:**

1. Проверочные записи делать **только** в выделенный каталог `/mnt/data/public/_migration-check/`. Пока пишется только он, откат остаётся бесплатным: при возврате каталог просто удаляется. Окно бесплатного отката закрывается на шаге 3, когда с папок Syncthing снимается пауза и записывать начинают партнёры.
2. Проверить сервисы сквозной записью, а не только чтением: интерфейс `filebrowser` показывает свой индекс из appdata, а `opds-generator` — кэш каталога, поэтому оба выглядят здоровыми даже поверх пустого каталога.
3. Развернуть Syncthing, снять паузу **по одной папке**, дождаться завершения пересканирования и сверить числа файлов с записанными в U2 прежде, чем размораживать следующую. Пересканирование будет полным и небыстрым: содержимое то же, но иноды новые, а контейнеру выделено пол-ядра. Состояние «Out of Sync» во время скана — нормально.
4. **Не нажимать `Revert Local Changes`.** Эта кнопка уничтожает файлы, существующие только локально. Если папка встала — сверять `Ignore Permissions` с записанным в U2 состоянием и разбираться, а не «чинить» кнопкой.
5. Смонтировать шары обратно на клиентах, удалить проверочный каталог.

```bash
cd /opt/homelab
./scripts/docker/deploy.sh syncthing
docker inspect syncthing --format '{{range .Mounts}}{{.Source}} -> {{.Destination}}
{{end}}'

# после записи тестового файла через шару Samba с клиента:
findmnt -T /mnt/data/public/_migration-check/проверка.txt
stat -c '%U:%G %a %n' /mnt/data/public/_migration-check/проверка.txt
```

**Сценарии проверки:**

- Запись через шару Samba: файл создаётся с клиента в `_migration-check`, `findmnt -T` показывает `/dev/md0`, владелец и права соответствуют ожидаемым для `public`.
- Чтение и запись через `filebrowser`: файлы видны, загрузка нового файла в `_migration-check` проходит, файл появляется на массиве.
- Syncthing на сервере: обе папки в состоянии `Up to Date`; тип каждой папки (Send / Receive / Receive Only) и `Ignore Permissions` — в том же положении, что записано в U2; число файлов и объём совпадают с записанными в U2. Только после этого снимается пауза на партнёрских устройствах; их числа файлов после синхронизации тоже совпадают с записанными.
- `opds-generator`: каталог открывается и книга по ссылке из него **скачивается** — это и есть доказательство, что каталог указывает на реальные файлы на массиве, а не на сохранённый у сервиса список.
- `backrest`: интерфейс открывается, план бэкапа appdata запускается вручную и завершается успешно (доказательство, что конфигурация rclone на месте).
- Ни один контейнер не имеет источников монтирования в `/mnt/data-tmp`.
- Проверочный каталог `_migration-check` удалён после проверки.

### U9. Вывод временного каталога из обращения

**Цель:** освободить место на системном диске, не потеряв путь отката раньше времени.

**Требования:** R9.

**Зависимости:** U8. Шаги 1–3 (проверка ссылок, переименование, нейтрализация резервной копии `.env`) выполняются в рамках этого плана. Шаг 4 — **необратимое удаление** — ждёт двух условий: неделя без обращений к старому пути и появление холодной копии данных вне зеркала (отдельная задача про диск `sdd`). До этого каталог `users` живёт только на зеркале: restic-планы бэкапят лишь appdata, а зеркало защищает от отказа диска, но не от удаления файла.

**Подход:**

```bash
# 1. Доказать, что на старый путь ничего не ссылается
grep -n DATA_PATH /opt/homelab/.env
docker ps -aq | xargs -r docker inspect \
  --format '{{.Name}} {{.State.Status}}{{range .Mounts}} {{.Source}}{{end}}' | grep data-tmp
grep -n data-tmp /etc/fstab
sudo find /mnt/data -type l -lname '*data-tmp*'
findmnt -R /mnt/data-tmp
findmnt -T /mnt/data-tmp

# 2. Переименовать
sudo mv /mnt/data-tmp /mnt/data-tmp.DELETE-20260818

# 3. Нейтрализовать резервную копию .env — она указывает на путь, которого больше нет
mv /opt/homelab/.env.bak-2026-08-18 \
   /opt/homelab/appdata/migration-2026-08-18/env.rollback-CLOSED

# 4. ГЕЙТ: неделя без поломок + холодная копия на sdd существует. Только тогда:
sudo rm -rf --one-file-system /mnt/data-tmp.DELETE-20260818
df -h /
sudo lsof +L1 | head
```

**Проверка:**

- Ни одна из проверок шага 1 не находит ссылок на старый путь; в частности `docker ps -aq` (со **остановленными** контейнерами, а не только запущенными) не даёт совпадений — остановленный контейнер с `restart: unless-stopped` пересоздал бы путь при следующем старте демона.
- `findmnt -R /mnt/data-tmp` не показывает вложенных точек монтирования; `findmnt -T /mnt/data-tmp` показывает, что это каталог на корневой ФС, а не отдельная точка монтирования (иначе удаление файлов не вернёт место на корень — см. «Вне периметра»).
- После переименования неделя проходит без обращений к старому пути и без его пересоздания.
- После удаления `df -h /` показывает возврат места; `lsof +L1` не показывает процессов, удерживающих удалённые файлы.

### U10. Обновление документации

**Цель:** документация описывает фактическое состояние, а не переходное.

**Требования:** R10.

**Зависимости:** U8. Выполняется до шага 4 в U9, а не после — иначе неактуальные утверждения живут в репозитории неделю и больше.

**Файлы:**

- `ENVIRONMENT.md` — удалить раздел «Переходное состояние» целиком; в «Планах по апгрейду» снять выполненный пункт про перенос.
- `CLAUDE.md` — в заметке про `/mnt/data` убрать фразу о том, что данные лежат в `/mnt/data-tmp`, а зеркало пустое.
- `backups/README.md` — сверить и поправить утверждения о расположении данных.
- `PLAN.md` — проверить, появились ли пункты, ставшие неактуальными.

**Подход:** менять только утверждения, ставшие ложными. Раздел про сам RAID1, приёмку дисков и таблицу дисков не трогать — они остаются верными. Добавить рядом с описанием `scripts/bootstrap.sh` предупреждение: не запускать его для «починки прав» на заполненном дереве данных (KTD6). Отметить защиту из U6 и `chattr +i` на подлежащем каталоге — иначе через полгода кто-нибудь снимет флаг, не понимая, зачем он.

**Проверка:** `grep -rn "data-tmp" --include="*.md" --exclude-dir=docs .` не находит утверждений в настоящем времени. Файлы в `docs/plans/` — исторические документы, из проверки исключены.

## Verification Contract

Гейты, каждый из которых обязателен перед переходом дальше:

1. **Перед копированием:** `/mnt/data` — примонтированный `/dev/md0`; ни один контейнер (включая остановленные) не привязан к `/mnt/data-tmp`; `fuser`/`lsof` по источнику пусты; манифест снят уже с неподвижного дерева.
2. **После копирования:** `rsync exit=0`; в логе нет ошибок; временных файлов оборванной передачи нет.
3. **Главный гейт:** `rsync -aHAXSn --itemize-changes /mnt/data-tmp/ /mnt/data/` печатает **ноль строк**; сверка по контрольным суммам всего дерева (тот же прогон с ключом `-c`) — тоже ноль строк.
4. **После деплоя:** `docker inspect` по всем сервисам не содержит `/mnt/data-tmp`.
5. **Защита:** при отмонтированном массиве деплой сервиса с томами данных прерывается ошибкой и не создаёт каталогов на корне.
6. **Функциональный:** файл, записанный через шару Samba, лежит на `/dev/md0` с ожидаемым владельцем; папки Syncthing в `Up to Date`; партнёры не получили удалений.
7. **Перед необратимым удалением:** нет ссылок на старый путь; прошла неделя после переименования; существует холодная копия вне зеркала.

**Что даёт ложную уверенность и гейтом быть не может:** совпадение `du -sh` (законно расходится из-за разрежённых файлов, жёстких ссылок, `lost+found` и резерва ext4, при этом слеп к потере расширенных атрибутов); «контейнеры в состоянии Up»; «интерфейс открывается» — `filebrowser` показывает индекс из appdata, `opds-generator` — кэш каталога, оба выглядят здоровыми поверх пустого каталога; код возврата, снятый после конвейера с `tee` — он относится к `tee`, а не к `rsync`.

## Откат

**Окно отката бесплатно** от завершения U5 до момента, когда в U8 снимается пауза с папок Syncthing. До этого в новое дерево пишет только выделенный каталог `/mnt/data/public/_migration-check/`, который откат просто удаляет. После снятия паузы Syncthing начинает подтягивать изменения от партнёров в новое дерево, и возврат `DATA_PATH` эти изменения потеряет.

**Процедура (внутри окна):**

```bash
cd /opt/homelab
# 1. Если Syncthing уже поднят — сначала поставить обе папки на паузу в интерфейсе.
# 2. Вернуть конфигурацию.
cp /opt/homelab/.env.bak-2026-08-18 .env
grep -n '^DATA_PATH=' .env      # должно быть DATA_PATH=/mnt/data-tmp

# 3. Развернуть по одному, Syncthing — последним и только если он был поднят.
./scripts/docker/deploy.sh samba
./scripts/docker/deploy.sh filebrowser
./scripts/docker/deploy.sh backrest
./scripts/docker/deploy.sh opds-generator
./scripts/docker/deploy.sh syncthing

rm -rf /mnt/data/public/_migration-check
```

Если `grep` на шаге 2 показывает `DATA_PATH=/mnt/data`, резервная копия испорчена (кто-то прошёл U5 повторно) — откатываться нечем, вписывать старое значение руками.

**Что закрывает откат необратимо:** удаление `/mnt/data-tmp` (U9, шаг 4); рассылка удалений партнёрам Syncthing; запуск `scripts/bootstrap.sh` для «починки прав» (KTD6). После выхода из окна возврат делается не переключением, а обратным `rsync` с ручным разбором расхождений.

## Definition of Done

- Все файлы перенесены; повторный проход `rsync` в режиме проверки печатает ноль строк.
- `DATA_PATH=/mnt/data`, все пять сервисов подняты и монтируют каталоги с массива.
- Сквозная запись через Samba и `filebrowser` проверена; папки Syncthing синхронны, партнёры целы.
- Деплой при незамонтированном массиве прерывается с ошибкой и не создаёт каталоги на корне; подлежащий каталог `/mnt/data` защищён `chattr +i`.
- `/mnt/data-tmp` переименован в `.DELETE-20260818`, резервная копия `.env` нейтрализована, ссылок на старый путь не осталось.
- Документация не описывает переходное состояние.

**Хвост за границей этого плана:** необратимое удаление `/mnt/data-tmp.DELETE-20260818` — после недели выдержки и появления холодной копии на диске `sdd` (отдельная задача).
